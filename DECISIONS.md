# Журнал архітектурних та інженерних рішень (Architecture Decision Log)

Цей документ ведеться відповідно до критерію A2 регламенту оцінювання для фіксації ключових інженерних виборів та аналізу компромісів (trade-offs).

---

### ADR-001: Вибір симуляційного підходу та відмова від фізичних контролерів
* **Контекст / Проблема:** Специфіка дисципліни вимагає мультиплатформності (Windows, Linux, macOS) та автоматизованого прогону тестів у CI/CD. Фізичні радіомодулі (Arduino/ESP32 через Serial/COM-порти) створюють залежність від платформних драйверів ОС (`System.IO.Ports` на Linux вимагає специфічних прав доступу), що унеможливлює тестування в хмарних віртуальних машинах GitHub Actions.
* **Рішення:** Реалізувати власне платформонезалежне дискретно-подійне ядро моделювання (`MeshSim.Engine`) у пам'яті рантайму .NET. Передавання пакетів моделюється як математична ймовірність на основі евклідової відстані та зон завад.
* **Наслідки:** Проєкт повністю автономний, надійно збирається та тестується на будь-якій ОС без зовнішнього апаратного забезпечення.

---

### ADR-002: Вибір фреймворку для кросплатформного графічного інтерфейсу
* **Контекст / Проблема:** Потрібно створити візуальний інтерфейс для відображення топології вузлів та зон завад у реальному часі, який має однаково працювати на Windows і Linux. Стандартний WPF та WinForms працюють лише на Windows.
* **Рішення:** Використання фреймворку **Avalonia UI** (патерн MVVM) замість WPF або MAUI (який не має офіційної стабільної підтримки десктопного Linux).
* **Наслідки:** Єдина кодова база XAML та C# компілюється та запускається на Linux (X11/Wayland), Windows та macOS без модифікацій.

### ADR-003: Інструментарій перевірки якості коду та контролю тестового покриття
* **Контекст / Проблема:** Критерії C3 та C4 вимагають покриття автотестами >=80% з інструментальним звітом, а також 0 критичних/major зауважень лінтера.
* **Рішення:** Увімкнення розширених Roslyn-аналізаторів (`AnalysisMode=Recommended`) у файлі `Directory.Build.props`. Для покриття використовуються два механізми Coverlet: `coverlet.msbuild` (`CollectCoverage=true` у `Directory.Build.props`, локальний звіт `coverage.json` і таблиця в консолі) та `coverlet.collector` (`--collect:"XPlat Code Coverage"`, формат Cobertura) у конвеєрі GitHub Actions.
* **Наслідки:** Помилки стилю коду та потенційні баги відловлюються ще на етапі компіляції. Наразі CI запускає збір покриття, але не публікує звіт і не перевіряє поріг. Це заплановано в Issue #28 («[CI] Publish coverage report, enforce 80% threshold and enable warnings as errors»), де також перевіряється сумісність двох механізмів в одному запуску.

### ADR-004: Вибір тестового фреймворку xUnit
* **Контекст / Проблема:** Необхідність забезпечення стабільного виконання тестів у headless-середовищі Ubuntu та Windows без додаткових зовнішніх раннерів.
* **Рішення:** Використання бібліотеки `xUnit` замість NUnit або MSTest.
* **Наслідки:** xUnit є нативним стандартом для сучасного .NET 8, підтримує ізоляцію тестових класів та паралельне виконання за замовчуванням, що скорочує час виконання CI-пайплайну.

### ADR-005: Оптимізація моделі геометрії вузлів пам'яттю
* **Контекст / Проблема:** У процесі моделювання сітки з десятків чи сотень вузлів постійно виконуються тисячі розрахунків відстаней між парами точок. Використання референсних типів для координат створює додаткові алокації в купі (heap) і навантаження на Garbage Collector.
* **Рішення:** Модель координат `Position` реалізована як легковажна незмінна структура `readonly record struct Position`.
* **Наслідки:** Координати зберігаються за значенням: у локальних змінних і параметрах методів вони живуть на стеку, а всередині класів (`MeshNode`, `JammingZone`) розміщуються інлайн у самому об'єкті без окремої алокації. Це зменшує кількість алокацій у гарячих обчисленнях відстаней. Структура не усуває алокацій повністю: події (`SimulationEvent`) містять посилання на `NetworkPacket` і рядки, які розміщуються в купі.

### ADR-006: Застосування патерна Strategy для протоколів маршрутизації
* **Контекст / Проблема:** У процесі розробки симулятора `MeshSim.Engine` постала потреба у гнучкому перемиканні між різними алгоритмами пошуку шляху (базовий алгоритм Дейкстри з урахуванням завад зараз, а в майбутньому — проактивні/реактивні протоколи для курсової роботи), не змінюючи код самого двигуна.
* **Рішення:** Виділено інтерфейс `IRoutingStrategy`, який реалізує патерн проєктування Strategy. Двигун симуляції залежить лише від абстракції.
* **Наслідки:** Дотримано принцип відкритості/закритості (OCP). Додавання нових алгоритмів маршрутизації не вимагає модифікації існуючого коду `SimulationEngine`.

### ADR-007: Використання `.NET PriorityQueue` для дискретно-подійного ядра (DES)
* **Контекст / Проблема:** Дискретно-подійний симулятор потребує ефективного планування та вилучення подій у хронологічному порядку за віртуальним часом. Постійне пересортування звичайних списків `List<T>` після кожної нової події має алгоритмічну складність `O(N log N)` або `O(N²)`.
* **Рішення:** Використання вбудованої у .NET 8 колекції `PriorityQueue<TElement, TPriority>` зі складеним ключем пріоритету `(double Timestamp, long Sequence)` для збереження порядку FIFO при однакових мітках часу.
* **Наслідки:** Забезпечено додавання та вилучення подій за `O(log N)`, що гарантує лінійно-логарифмічну швидкодію симуляції при масштабуванні кількості пакетів.

### ADR-008: Покроковий API рушія та незалежні знімки стану (Step / GetSnapshot)
* **Контекст / Проблема:** Інтерфейс (Play/Pause/Step/Reset) має керувати симуляцією по одній події. Існуючий `RunToCompletion()` монолітний. Крім того, він повертав `EventLog` як живе представлення внутрішнього списку (`AsReadOnly()`), через що раніше отриманий результат змінювався при наступних запусках.
* **Рішення:** Виділено `Step()` (обробка однієї події, повертає її або `null`), `HasPendingEvents` і `GetSnapshot()`, який будує `SimulationResult` із копіями журналу та розбивки втрат. `RunToCompletion()` реалізовано як цикл `Step()` з подальшим `GetSnapshot()`. Розглянуті й відкинуті альтернативи: події/колбеки (`IObservable`), `RunUntil(timeMs)` (додається поверх `Step()` за потреби).
* **Наслідки:** UI отримує детермінований покроковий режим, а покроковий і пакетний прогони дають однаковий результат (закріплено тестом). Компроміси: кожен знімок копіює журнал за O(n); події у знімку посилаються на ті самі об'єкти `NetworkPacket`, тож `Ttl`/`HopCount` пакета можуть змінитися пізнішими кроками; доставка рахується в момент передачі останнього стрибка, а подія `PacketDelivered` потрапляє в журнал на `HopDelayMs` пізніше.

### ADR-009: Сценарій як DTO зі схемою та фабрика свіжого рушія
* **Контекст / Проблема:** `SimulationEngine` змінює стан вузлів (заряд) і пакетів (TTL, HopCount), тому повторний запуск на тих самих об'єктах дає інший результат. Інтерфейсу потрібні Reset, збереження та відкриття сцени; файли потребують валідації та версіонування (критерій C5).
* **Рішення:** Сценарій описується незмінним DTO `ScenarioDefinition` (вузли, зони завад і пакети окремими списками; пакети посилаються на вузли за `SourceNodeId`/`DestinationNodeId`; параметри рушія; ключ стратегії маршрутизації рядком через `RoutingStrategyRegistry`; `schemaVersion`). JSON читається суворо (`UnmappedMemberHandling.Disallow`). `ScenarioValidator` збирає всі помилки (унікальність Id в межах типу сутності, існування вузлів-посилань, межі значень, версія схеми) з індексацією через `HashSet`. `ScenarioFactory` щоразу будує нову топологію та новий рушій; Reset є повторною побудовою. Запис виконується атомарно (`AtomicFileWriter`: тимчасовий файл і `File.Move(overwrite: true)` з очищенням у `finally`).
* **Наслідки:** Перезапуск детермінований, а збереження не може залишити напівзаписаний файл. Некоректний сценарій не потрапляє на диск і не будується в рушій. Компроміси: валідація DTO частково дублює перевірки конструкторів доменних класів (навмисно: валідатор повертає всі помилки одразу, а конструктори кидають на першій); підтримується лише схема версії 1 без міграцій; операції файлового вводу синхронні, що достатньо для сценаріїв малого розміру.

### ADR-010: Формат і цілісність звітів симуляції (JSON/CSV, SHA-256, захист CSV)
* **Контекст / Проблема:** Результати прогону потрібно зберігати для аналізу та повторного відкриття (критерій C5). Файли можуть бути пошкоджені, змінені вручну або відкриті в електронних таблицях, де текст, що починається зі знака формули, виконується (CSV Formula Injection).
* **Рішення:** Повний звіт (метрики, розбивка втрат, журнал подій, `schemaVersion`) експортується в JSON, а журнал подій в CSV. Для кожного файлу поруч створюється файл `шлях.sha256` із SHA-256 від тих самих байтів, що записані на диск. Запис атомарний (`AtomicFileWriter`). У CSV текстові поля, що починаються з `=`, `+`, `-`, `@`, табуляції чи `\r`, отримують префікс `'`, далі діє екранування за RFC 4180; числа форматуються через `InvariantCulture`. Імпорт обмежено JSON: перевіряється сума, суворий розбір, узгодженість метрик (через інваріанти конструктора `SimulationResult`), PDR, назви причин і типів подій, хронологія. Результат імпорту це `ReportDocument`, а не `SimulationResult`: пакети подій неможливо відновити, бо звіт не містить початкового TTL і розміру навантаження.
* **Наслідки:** Випадкове пошкодження або ручне редагування звіту виявляється при імпорті; відкриття CSV у таблиці не виконує формул. Компроміси: SHA-256 без ключа не захищає від навмисної підміни (зловмисник може перерахувати суму; для автентичності потрібен HMAC чи підпис); запис звіту та суми це два окремі атомарні записи, тому збій між ними лишає звіт без суми й він відхиляється при імпорті; префікс `'` робить експорт ідентифікаторів на кшталт `-node` необоротним, тому CSV є лише форматом для зовнішнього аналізу.

### ADR-011: Структура Desktop-проєкту, межа тестованості та відмовостійкість запуску
* **Контекст / Проблема:** Критерії C3 і C4 вимагають високого покриття та 0 зауважень аналізатора, але код Avalonia (XAML, елементи, `DrawingContext`) неможливо розумно покрити unit-тестами без графічного середовища. Крім того, критерій C2 вимагає обробки винятків без аварійного завершення та відсутності необроблених винятків у журналі.
* **Рішення:** Проєкт `MeshSim.Desktop` (`net8.0`, без `-windows`, щоб збиратись на Ubuntu та Windows) поділено на тонкий візуальний шар і тестований шар. Візуальні класи (`Program`, `App`, `MainWindow`, `ErrorDialogNotifier`, `AppServices`, кастомні контролі) позначено `[ExcludeFromCodeCoverage]` із текстовим обґрунтуванням. Уся логіка (ViewModels, журнал, обробник винятків, математика карти) винесена в окремі публічні класи без цього атрибута і покривається тестами в `MeshSim.Tests`. Coverlet інструментує лише збірки `MeshSim.*` (`Include`) і не враховує службові типи `CompiledAvaloniaXaml.*` (`Exclude`). MVVM побудовано на `ObservableObject` з CommunityToolkit.Mvvm без source-генераторів. Файловий журнал (`FileLogger`) ротується за датою, потокобезпечний і ніколи не кидає винятків; глобальний обробник (`GlobalExceptionHandler`) реєструється на `AppDomain.UnhandledException`, `TaskScheduler.UnobservedTaskException` та винятках UI-потоку, логує, показує діалог і сам не кидає. Версії: Avalonia 11.3.x (підтримувана лінійка 11) замість 12.x, яка має breaking changes.
* **Наслідки:** Розрахунок покриття відображає якість логіки, а не обсяг XAML. Збій запису журналу чи показу діалогу не завалює застосунок. Компроміси: візуальний шар перевіряється лише вручну (та в приймальних кейсах); статичний `AppServices` є простим композиційним коренем без контейнера залежностей; фільтри покриття мають підтримуватись при додаванні нових візуальних класів; перехід на Avalonia 12 вимагатиме окремої міграції.

### ADR-012: Побудова сцени карти як чистої функції (ViewportTransform, MapSceneBuilder)
* **Контекст / Проблема:** Карта топології має показувати вузли, радіуси, лінки за якістю, зони завад і заряд. Код малювання через `DrawingContext` неможливо тестувати без графічного середовища, а критерій C3 вимагає 100% покриття логіки.
* **Рішення:** Відображення розділено на три шари. (1) `ViewportTransform` перетворює світові координати (метри, Y вгору) на екранні (пікселі, Y вниз) із рівномірним масштабом, відступами та центруванням; захищений від нульового вікна й виродженої області. (2) `MapSceneBuilder` будує незалежний від Avalonia `MapScene` (екранні координати та стилі з `LinkStyleCalculator`, `NodeStyleCalculator`, `ZoneStyleCalculator`; колір описано власним `RgbaColor`). (3) `MapControl` лише малює готові примітиви й виключений із покриття. Лінк показується, якщо радіодосяжний хоча б один напрямок, а якість це максимум якостей двох напрямків; повністю заглушений канал лишається видимим червоним пунктиром. Вузли й лінки впорядковуються за Id для детермінованості.
* **Наслідки:** Уся логіка відображення покрита unit-тестами, а контрол містить лише виклики малювання. Компроміси: сцена перебудовується повністю при кожній зміні розміру чи стану (складність побудови лінків O(n²), прийнятно для десятків вузлів); масштаб лише «вписати» без ручного зуму й панорамування; кола радіусів передачі при щільному розміщенні перекриваються; розмір вузла фіксований у пікселях і не масштабується зі світом.

### ADR-013: Керування симуляцією через абстракцію таймера та візуалізація активного пакета
* **Контекст / Проблема:** Інтерфейс має запускати, призупиняти й виконувати симуляцію покроково, показувати живі метрики, журнал подій і поточне положення пакета на карті. Прямий `DispatcherTimer` у ViewModel робить керування неможливим для unit-тестування без UI-потоку, а критерій C3 вимагає 100% покриття логіки.
* **Рішення:** Таймер винесено за інтерфейс `ISimulationTimer` (`IsRunning`, `Interval`, `Tick`, `Start`, `Stop`); обгортка `AvaloniaSimulationTimer` над `DispatcherTimer` виключена з покриття, а в тестах використовується `ManualSimulationTimer` із явним `FireTick()`. `SimulationViewModel` реалізує автомат станів `Ready → Running ⇄ Paused → Finished` поверх `SimulationEngine.Step()`/`GetSnapshot()`: тік виконує крок лише в стані `Running`, а коли подій більше немає, таймер зупиняється сам. `Reset` будує новий `ScenarioRuntime` через `ScenarioFactory.Build`, очищає журнал і метрики та скидає активність на карті. Швидкість задається множником (0.25×…4×) від базового інтервалу 800 мс. Для карти ViewModel запам'ятовує останній вузол кожного пакета й передає в `MapSceneBuilder` `PacketActivity` (пакет, вузол, попередній вузол, тип події, причина втрати); `MapSceneBuilder` повертає маркер на вузлі події та підсвічений сегмент від попереднього вузла. Усі розрахунки координат і кольорів лишаються в `Rendering` і покриті тестами, а `MapControl` лише малює.
* **Наслідки:** Play/Pause/Step/Reset, автоматична зупинка, зміна швидкості та скидання повністю тестуються синхронно. Компроміси: кожен крок викликає `GetSnapshot()` (копія журналу за O(n)) і повну перебудову сцени, що прийнятно для сотень подій; журнал в інтерфейсі необмежений за розміром; маркер стоїть на вузлі, а не рухається вздовж сегмента (плавну анімацію можна додати поверх `PacketActivity`); лічильник доставлених зростає в момент передачі останнього стрибка, тоді як подія `PacketDelivered` у журналі з'являється на `HopDelayMs` пізніше (поведінка рушія з ADR-008).

### ADR-014: Редагування сцени як перетворення незмінного сценарію з валідацією та перезавантаженням прогону
* **Контекст / Проблема:** Користувач має змінювати сцену на карті (перетягувати вузли й зони, додавати та видаляти об'єкти, перемикати зони, планувати пакети), не ламаючи ні симуляцію, ні цілісність даних (C2, C5), а логіка редагування має бути тестована без UI (C3). `SimulationEngine` змінює стан вузлів і пакетів, тому «живе» редагування топології під час прогону дало б неузгоджені результати.
* **Рішення:** (1) `ScenarioDefinition` лишається незмінним, а редагування це чисті функції `ScenarioEditing` (`ScenarioDefinition → ScenarioDefinition`, незмінені розділи передаються за посиланням). (2) Усі правки проходять через єдиний `Apply` редактора: дозволено лише поза станом `Running` (бо `RelayCommand.Execute` не перевіряє `CanExecute`) → `ScenarioValidator.Validate` → `SimulationViewModel.LoadScenario`, який спершу будує новий `ScenarioRuntime` (некоректний сценарій відхиляється до зміни стану), зупиняє таймер і скидає прогін. Помилки парсингу (текстові поля, `InvariantCulture`, десяткова крапка) та валідації потрапляють у `ErrorMessage`/`HasError` без винятків. (3) Hit-testing винесено в чисту функцію `MapHitTester` (вузли над зонами; найближчий вузол; найменша зона серед вкладених) над готовою `MapScene`. (4) Перетягування: `MapViewModel.BeginDrag/EndDrag` заморожують перетворення світ → екран (інакше автовписування за межами топології «тікало» б з-під курсора), нова позиція = початкова + зсув курсора у світових координатах із округленням до 0.1 (без стрибка центру до курсора); `MapControl` лише делегує `PointerPressed/Moved/Released` редактору. (5) Виділення зберігається в `MapViewModel` і зберігається при заміні топології, якщо об'єкт існує. (6) Видалення вузла, на який посилаються пакети, відхиляється валідатором, без каскадного видалення.
* **Наслідки:** Правки детерміновані, тестовані й не можуть залишити сцену в некоректному стані; `Simulation.Scenario` є готовим джерелом для збереження у файл (#26). Компроміси: кожна правка (і кожен рух миші) перебудовує рантайм і скидає прогін, що прийнятно для десятків вузлів, але не масштабується на тисячі; немає скасування (undo); після відпускання миші вид вписується заново і може трохи змінити масштаб; список пакетів оновлюється лише при зміні самого списку (порівняння посилань), тому операції над вузлами та зонами мусять передавати той самий список пакетів; журнал фіксує лише завершення перетягування, а не кожен рух.

### ADR-015: Файловий ввід-вивід в інтерфейсі через абстракцію діалогів та єдину точку обробки помилок
* **Контекст / Проблема:** Користувач має відкривати й зберігати сценарії, експортувати звіти (JSON/CSV з контрольними сумами) та відкривати збережені звіти. Системні діалоги вибору файлів (`StorageProvider`) неможливо тестувати без вікна, а помилки файлів (пошкоджений вміст, непідтримувана схема, підроблений звіт, відсутній доступ) не мають ні завалювати застосунок, ні псувати поточну сцену (критерії C2, C5, C3).
* **Рішення:** (1) Діалоги винесено за інтерфейс `IFileDialogService` (`null` означає скасування); реалізація `AvaloniaFileDialogService` виключена з покриття, а в тестах використовується `StubFileDialogService`. (2) `FileOperationsViewModel` виконує всі файлові операції через єдиний `RunFileOperation`, де перехоплюються лише очікувані помилки (`InvalidDataException`, `IOException`, `UnauthorizedAccessException`; фільтр `IsExpectedFileFailure`, одна обґрунтована суперечність із CA1031); інші винятки не ховаються й доходять до `GlobalExceptionHandler`. Помилка логується, показується користувачу з поясненням і потрапляє в статус; успіх логується та показується в статусі; скасований діалог тихо завершує команду. (3) Сцена не псується, бо `ScenarioFile.Load` валідує файл до виклику `LoadScenario`, а при невдалому імпорті звіту лишається попереднє резюме. (4) «Відкрити сценарій» заблоковано під час `Running`, перевірка стоїть після діалогу (користувач міг натиснути «Старт», поки той був відкритий). (5) Імпорт звіту показує текстове резюме (`ReportSummaryFormatter`), а не відновлену симуляцію, бо `ReportDocument` не містить даних для відновлення пакетів (ADR-010). (6) Каталог `scenarios/` містить три приклади, кожен із яких перевіряється тестом (завантаження, побудова, запуск і очікувані метрики).
* **Наслідки:** Усі гілки файлових команд (скасування, успіх, пошкоджений файл, підроблена сума, помилка диска) перевіряються синхронно й повторювано, а користувач завжди бачить причину збою. Компроміси: читання та запис виконуються синхронно в UI-потоці (достатньо для малих файлів, великі потребували б `Task.Run`); збереження й експорт блокують UI на час запису; не виконується автозбереження чи перевірка «незбережених змін» перед відкриттям іншого сценарію; сума SHA-256 без ключа захищає від випадкового пошкодження, а не від навмисної підміни (ADR-010); приклад `battery-depletion.json` спирається на поведінку рушія, за якої остання передача релея з нульовим залишком заряду фіксується як `JammedInTransit`.
