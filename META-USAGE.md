# Декларація використання інструментів генеративного ШІ (META-USAGE)

Цей документ складено відповідно до регламенту курсу «Мультиплатформне програмування» (розділ 7.1.1 «Академічна доброчесність і політика щодо ШІ»).

## 1. Застосовані інструменти
* **Модель / Інструмент:** Google Gemini
* **Середовище використання:** Вебінтерфейс взаємодії

---

## 2. Принципи застосування, переваги та обмеження

### Принципи (Стратегія застосування)
1. **AI як асистент архітектора, а не заміна розробника:** ШІ використовується для швидкої декомпозиції технічних вимог, генерації базових шаблонів коду та конфігурацій інфраструктури.
2. **Усвідомлене перенесення замість копіпасту (Active Coding & Zero Blind Trust):** повна відмова від сліпого копіювання згенерованих фрагментів. Код набирається та адаптується вручну; розробник самостійно аналізує семантику кожного рядка, контролює типи даних та самостійно усуває помилки компіляції й розбіжності середовища перед коммітом.
3. **Платформонезалежність:** контроль того, щоб пропоновані рішення не містили прихованих Win32 API або прив'язок до специфічного заліза.

### Переваги (Advantages)
* Суттєве прискорення рутинних операцій (шаблонізація проектів у .NET CLI, складання YAML для CI/CD матриці).
* Швидкий аналіз та мапінг критеріїв оцінювання курсу на конкретні технічні завдання (Issues).
* Ефективний брейнштормінг предметної області моделювання mesh-мереж та розрахунку зон радіозавад.

### Обмеження (Limitations)
* **Ризик галюцинацій та застарілого синтаксису:** моделі можуть пропонувати API застарілих версій .NET Framework або некоректні параметри нових версій .NET 8/9.
* **Відсутність контексту компіляції:** ШІ генерує код ізольовано, тому не здатен гарантувати відсутність попереджень суворого аналізатора (Roslyn Analyzers) без ручної доробки.
* **Алгоритмічні спрощення:** згенеровані моделі часто ігнорують межові випадки (наприклад, нульовий час життя TTL, ділення на нуль при збігу координат), що вимагає ручного написання тестів на граничні умови.

## 3. Ключові запити та згенеровані артефакти

### Етап 1 (Чекпоінт 1): Інфраструктура та базовий домен
* **Запит 1 (Конфігурація CI/CD):** «Складання GitHub Actions workflow із матричною збіркою під Ubuntu та Windows і збором XPlat Code Coverage».
  * *Роль ШІ та доопрацювання:* Згенеровано базовий шаблон `.github/workflows/ci.yml`, який було адаптовано під структуру рішення `ResilientMesh.sln` та `global.json`.
* **Запит 2 (Контракти сутностей ядра):** «Обговорення контрактів класів Position, MeshNode, NetworkPacket на C# 12 / .NET 8».
  * *Роль ШІ та доопрацювання:* Узгоджено сигнатури методів; розробником самостійно реалізовано валідацію граничних станів (`double.IsNaN`, `double.IsInfinity`), логіку витрати заряду та переведено `Position` на `readonly record struct`.

### Етап 2 (Чекпоінт 2): Движок симуляції, маршрутизація та верифікація покриття
* **Запит 3 (Математична модель перетину лінії зв'язку з колом завади):** «Алгоритм проекції точки на відрізок для перевірки перетину радіоканалу між двома вузлами з круглою зоною РЕБ».
  * *Роль ШІ та доопрацювання:* Отримано математичну формулу параметричної проекції `t` на відрізок. Розробником інтегровано формулу в клас `JammingZone`, додано обробку вироджених відрізків (коли координати початку і кінця збігаються) та облік стану активності зони.
* **Запит 4 (Декомпозиція дискретно-подійного циклу та алгоритму Дейкстри):** «Обговорення архітектури черги подій на базі .NET PriorityQueue та штрафних функцій ваги ребра для обходу завад».
  * *Роль ШІ та доопрацювання:* ШІ запропонував базовий концепт циклу подій. Під час власної реалізації та інженерного рев'ю розробником виявлено та самостійно усунено низку архітектурних крайніх випадків:
    1. У `SimulationEngine` додано складений ключ пріоритету `(Timestamp, Sequence)` для гарантування детермінованого порядку FIFO при однакових мітках часу, а також захист від планування подій у минулому (`timestampMs < CurrentTimeMs`).
    2. Розділено стани відсутності вузла в топології (`PacketDropReason.NodeNotFound`) та вичерпання заряду батареї (`NodeBatteryDepleted`).
    3. У класі `SimulationResult` виявлено відсутність контролю цілісності метрик у початковій концепції — розробником додано перевірки інваріантів (`delivered + dropped <= sent` із захистом від переповнення `int` через приведення до `long` та звірку суми словника `DropsByReason`).
* **Запит 5 (Аналіз звіту Coverlet та пошук граничних тест-кейсів):** «Аналіз звіту покриття Coverlet для виявлення непокритих гілок розгалужень (branch coverage) та генерація ідей граничних тестів».
  * *Роль ШІ та доопрацювання:* ШІ використано для швидкого парсингу JSON-звіту покриття та генерації шаблонних тестових методів `[Theory] / [InlineData]`. Розробником самостійно спроєктовано складні тестові сценарії, зокрема тестовий дублер (stub) `FixedRouteStrategy` для примусового тестування стану `JammedInTransit` в обхід розумної маршрутизації Дейкстри, що дозволило вивести Line та Branch Coverage обох модулів на рівень 100%.

## 4. Методи верифікації та контролю якості

1. **Статичний аналіз коду:** підключено `AnalysisMode=Recommended` у `Directory.Build.props`. Згенерований код відредаговано так, щоб збірка проходила з 0 критичних/major зауважень лінтера.
2. **Модульне тестування:** створено набір xUnit тестів у проєкті `MeshSim.Tests`, що перевіряють коректність розрахунків відстаней, декременту TTL та споживання енергії.
3. **Контроль покриття:** налаштовано інструмент Coverlet для контролю того, що рівень покриття коду тестами досяг 100%.
4. **Кросплатформна перевірка:** проходження збірки та тестів підтверджується автоматично на віртуальних машинах Linux (Ubuntu) та Windows у GitHub Actions.
5. **Самостійний локальний траблшутинг та налагодження:** помилки компілятора, невідповідності регістру синтаксичних конструкцій платформи та зауваження Roslyn-аналізаторів (зокрема правила іменування на кшталт CA1707) діагностуються та виправляються розробником безпосередньо в середовищі розробки через CLI/IDE.
