# Декларація використання інструментів генеративного ШІ (META-USAGE)

Цей документ складено відповідно до регламенту курсу «Мультиплатформне програмування» (розділ 7.1.1 «Академічна доброчесність і політика щодо ШІ»).

## 1. Застосовані інструменти
* **Модель / Інструмент:** Google Gemini
* **Середовище використання:** Вебінтерфейс взаємодії

---

## 2. Принципи застосування, переваги та обмеження

### Принципи (Стратегія застосування)
1. **AI як асистент архітектора, а не заміна розробника:** ШІ використовується для швидкої декомпозиції технічних вимог, генерації базових шаблонів коду та конфігурацій інфраструктури.
2. **Усвідомлене перенесення замість копіпасту (Active Coding & Zero Blind Trust):** повна відмова від сліпого копіювання згенерованих фрагментів. Код набирається та адаптується вручну; розробник самостійно аналізує семантику кожного рядка, контролює типи даних та самостійно усуває помилки компіляції й розбіжності середовища перед коммітом.
3. **Платформонезалежність:** контроль того, щоб пропоновані рішення не містили прихованих Win32 API або прив'язок до специфічного заліза.

### Переваги (Advantages)
* Суттєве прискорення рутинних операцій (шаблонізація проектів у .NET CLI, складання YAML для CI/CD матриці).
* Швидкий аналіз та мапінг критеріїв оцінювання курсу на конкретні технічні завдання (Issues).
* Ефективний брейнштормінг предметної області моделювання mesh-мереж та розрахунку зон радіозавад.

### Обмеження (Limitations)
* **Ризик галюцинацій та застарілого синтаксису:** моделі можуть пропонувати API застарілих версій .NET Framework або некоректні параметри нових версій .NET 8/9.
* **Відсутність контексту компіляції:** ШІ генерує код ізольовано, тому не здатен гарантувати відсутність попереджень суворого аналізатора (Roslyn Analyzers) без ручної доробки.
* **Алгоритмічні спрощення:** згенеровані моделі часто ігнорують межові випадки (наприклад, нульовий час життя TTL, ділення на нуль при збігу координат), що вимагає ручного написання тестів на граничні умови.

## 3. Ключові запити та згенеровані артефакти

### Етап 1 (Чекпоінт 1): Інфраструктура та базовий домен
* **Запит 1 (Конфігурація CI/CD):** «Складання GitHub Actions workflow із матричною збіркою під Ubuntu та Windows і збором XPlat Code Coverage».
  * *Роль ШІ та доопрацювання:* Згенеровано базовий шаблон `.github/workflows/ci.yml`, який було адаптовано під структуру рішення `ResilientMesh.sln` та `global.json`.
* **Запит 2 (Контракти сутностей ядра):** «Обговорення контрактів класів Position, MeshNode, NetworkPacket на C# 12 / .NET 8».
  * *Роль ШІ та доопрацювання:* Узгоджено сигнатури методів; розробником самостійно реалізовано валідацію граничних станів (`double.IsNaN`, `double.IsInfinity`), логіку витрати заряду та переведено `Position` на `readonly record struct`.

### Етап 2 (Чекпоінт 2): Движок симуляції, маршрутизація та верифікація покриття
* **Запит 3 (Математична модель перетину лінії зв'язку з колом завади):** «Алгоритм проекції точки на відрізок для перевірки перетину радіоканалу між двома вузлами з круглою зоною РЕБ».
  * *Роль ШІ та доопрацювання:* Отримано математичну формулу параметричної проекції `t` на відрізок. Розробником інтегровано формулу в клас `JammingZone`, додано обробку вироджених відрізків (коли координати початку і кінця збігаються) та облік стану активності зони.
* **Запит 4 (Декомпозиція дискретно-подійного циклу та алгоритму Дейкстри):** «Обговорення архітектури черги подій на базі .NET PriorityQueue та штрафних функцій ваги ребра для обходу завад».
  * *Роль ШІ та доопрацювання:* ШІ запропонував базовий концепт циклу подій. Під час власної реалізації та інженерного рев'ю розробником виявлено та самостійно усунено низку архітектурних крайніх випадків:
    1. У `SimulationEngine` додано складений ключ пріоритету `(Timestamp, Sequence)` для гарантування детермінованого порядку FIFO при однакових мітках часу, а також захист від планування подій у минулому (`timestampMs < CurrentTimeMs`).
    2. Розділено стани відсутності вузла в топології (`PacketDropReason.NodeNotFound`) та вичерпання заряду батареї (`NodeBatteryDepleted`).
    3. У класі `SimulationResult` виявлено відсутність контролю цілісності метрик у початковій концепції — розробником додано перевірки інваріантів (`delivered + dropped <= sent` із захистом від переповнення `int` через приведення до `long` та звірку суми словника `DropsByReason`).
* **Запит 5 (Аналіз звіту Coverlet та пошук граничних тест-кейсів):** «Аналіз звіту покриття Coverlet для виявлення непокритих гілок розгалужень (branch coverage) та генерація ідей граничних тестів».
  * *Роль ШІ та доопрацювання:* ШІ використано для швидкого парсингу JSON-звіту покриття та генерації шаблонних тестових методів `[Theory] / [InlineData]`. Розробником самостійно спроєктовано складні тестові сценарії, зокрема тестовий дублер (stub) `FixedRouteStrategy` для примусового тестування стану `JammedInTransit` в обхід розумної маршрутизації Дейкстри, що дозволило вивести Line та Branch Coverage обох модулів на рівень 100%.

  ### Етап 3 (Чекпоінт 3): UI, файли, експорт, реліз
* **Запит 6 (Покроковий API рушія, Issue #19):** «Декомпозиція `RunToCompletion()` на `Step()`, `HasPendingEvents` та `GetSnapshot()`; план тестів без втрати 100% покриття».
  * *Роль ШІ та доопрацювання:* ШІ запропонував структуру API та набір тест-кейсів. Розробником перевірено семантику знімка: виявлено, що `EventLog` у `RunToCompletion()` був живим представленням списку (`AsReadOnly()`), змінено на копію (`ToArray()`) і додано регресійний тест; підтверджено, що доставка рахується у момент передачі останнього стрибка, а подія `PacketDelivered` потрапляє в журнал із затримкою `HopDelayMs`, і цю семантику зафіксовано тестом. Код написано вручну, збірку й покриття перевірено локально (0 попереджень, 100% Line/Branch для Engine).
* **Запит 7 (Модель сценарію та JSON, Issue #20):** «Структура DTO сценарію, реєстр стратегій маршрутизації, валідація цілісності (унікальні Id, зовнішні ключі пакетів, межі значень), суворий JSON, атомарний запис файлу».
  * *Роль ШІ та доопрацювання:* ШІ запропонував декомпозицію на `ScenarioDefinition`/`ScenarioValidator`/`ScenarioFactory`/`AtomicFileWriter` та перелік тест-кейсів. Розробником перевірено та зафіксовано: валідатор збирає всі помилки замість зупинки на першій; невідомі поля JSON відхиляються; Reset реалізовано як повторну побудову рушія; збереження не залишає тимчасових файлів навіть при збої переміщення (покрито тестом із зайнятим цільовим шляхом). Код написано вручну, збірку та покриття перевірено локально.
* **Запит 8 (Експорт і імпорт звітів, Issue #21):** «Формат звіту JSON/CSV, контрольна сума SHA-256, захист від CSV Formula Injection, валідація звіту при імпорті».
  * *Роль ШІ та доопрацювання:* ШІ запропоновано базову архітектуру `ReportExporter`, `CsvReportExporter`, `ReportValidator`, `ReportImporter` та концепт супутнього файлу контрольної суми (`.sha256`). Під час інженерного рев'ю та адаптації коду розробником:
    1. **Архітектурне розділення DTO та Domain:** відхилено початкову ідею десеріалізації файлу напряму в `SimulationResult`, оскільки відновлення повноцінних сутностей `NetworkPacket` неможливе без початкових параметрів (початковий TTL, PayloadBytes); замість цього спроєктовано незалежний DTO `ReportDocument`.
    2. **Усунення дублювання інваріантів (DRY):** перевірку узгодженості метрик у `ReportValidator` реалізовано через виклик конструктора доменного `SimulationResult` як єдиного джерела істини правил цілісності, замість дублювання математичних формул.
    3. **Аналіз безпеки та обмежень:** зафіксовано необоротність санітизації CSV-полів через префікс `'` (за стандартом OWASP проти Formula Injection) та обмеження непідписаного SHA-256 (гарантія цілісності від пошкодження, але не автентичності від підміни без HMAC).
    4. **Локальний траблшутинг та тестування:** виправлено конфлікт доступу між тестовою збіркою та внутрішніми методами експортера, узгоджено формулювання помилок схеми у валідаторі та тестах; досягнуто 100% покриття коду без попереджень Roslyn.
* **Запит 9 (Каркас Avalonia, логування та глобальний обробник винятків, Issue #22):** «Структура кросплатформного проєкту `MeshSim.Desktop` для Ubuntu та Windows, розмежування покриття тестами між XAML та бізнес-логікою, потокобезпечний файловий журнал, глобальний перехоплювач винятків».
  * *Роль ШІ та доопрацювання:* ШІ згенеровано базову структуру `MeshSim.Desktop` на Avalonia 11.3 та `CommunityToolkit.Mvvm` (без використання source-генераторів для уникнення конфліктів зі статичним аналізатором Roslyn). Під час інженерного опрацювання розробником:
    1. **Контроль тестового покриття (C3):** візуальні класи ініціалізації та вікон ізольовано атрибутом `[ExcludeFromCodeCoverage]`, а в `MeshSim.Tests.csproj` налаштовано фільтри `Include`/`Exclude` для відсікання синтетичних класів XAML-компілятора (`CompiledAvaloniaXaml.*`).
    2. **Відмовостійкість (C2):** реалізовано потокобезпечний `FileLogger` із добовою ротацією та перехопленням помилок вводу/виводу (`IOException`, `UnauthorizedAccessException`), що гарантує відсутність каскадного падіння при недоступності диска; `GlobalExceptionHandler` підключено до трьох каналів (`AppDomain`, `TaskScheduler`, `Dispatcher.UIThread`).
    3. **Верифікація:** усі класи логування, сповіщення та `MainViewModel` покрито модульними тестами на 100%; роботу діалогу помилок та запис у лог перевірено локальним запуском.
* **Запит 10 (2D-карта топології та чиста модель сцени, Issue #23):** «Математичне перетворення світових координат у екранні (`ViewportTransform`), розрахунок стилів лінків за якістю каналу та вузлів за зарядом, побудова сцени без залежності від UI-фреймворку, кастомний контрол рендерингу».
  * *Роль ШІ та доопрацювання:* ШІ запропонував трирівневий конвеєр рендерингу (`ViewportTransform` -> `MapSceneBuilder` -> `MapControl`). Розробником виконано верифікацію та доопрацювання:
    1. **Архітектурна ізоляція:** колір представлено власною структурою `RgbaColor`, а всі геометричні розрахунки (інверсія екранної осі Y, масштабування з відступами, захист від ділення на нуль при виродженій топології з одного вузла або нульовому розмірі вікна) винесено у чисті функції, на 100% покриті unit-тестами.
    2. **Візуальна інформативність:** реалізовано градієнтне кодування заряду батареї та якості радіоканалів; повністю подавлені РЕБ канали відображаються червоним пунктиром замість зникнення з карти, що дозволяє візуально оцінювати заблоковані напрямки.
    3. **Перевірка демонстраційного сценарію:** спроєктовано та верифіковано тестовий граф із 6 вузлів та 2 зон завад (`DemoScenario`), на якому підтверджено коректну побудову обхідного маршруту Дейкстри (`N1 -> N4 -> N3 -> N5`) в обхід зашумленої ділянки.
* **Запит 11 (Керування симуляцією, живі метрики та візуалізація активного пакета, Issue #24):** «Абстракція таймера для тестування Play/Pause, автомат станів симуляції поверх покрокового API, панель метрик та журналу, відображення активного пакета й сегмента передачі на карті».
  * *Роль ШІ та доопрацювання:* За допомогою ШІ згенеровано каркас `SimulationViewModel`, панелі метрик і подій та модель `PacketActivity`. Під час інженерного рев'ю та адаптації розробником:
    1. **Пряму залежність** від `DispatcherTimer` замінено на абстракцію `ISimulationTimer` із тестовим дублером `ManualSimulationTimer`, що дозволило детерміновано протестувати всі переходи автомата станів (`Ready → Running ⇄ Paused → Finished`) та регулювання швидкості без участі UI-потоку.
    2. **Додано** відстеження попередніх вузлів пакетів (`_lastNodeByPacket`), завдяки чому реалізовано графічне підсвічування активних радіоканалів і виведення причини скидання біля маркера на карті.
    3. **Виправлено** зауваження аналізатора Roslyn (`CA1859` щодо конкретних типів повернення у приватних методах) та забезпечено 100% покриття нового функціоналу автотестами (Method, Line та Branch Coverage).
* **Запит 12 (Інтерактивне редагування сцени та валідація форм, Issue #25):** «Обговорення паттерну незмінних трансформацій сценарію, алгоритму геометричного hit-testing об'єктів карти та способу стабілізації координат під час перетягування».
  * *Роль ШІ та доопрацювання:* ШІ використано для брейнштормінгу структури взаємодії між картою і панеллю редактора та генерації граничних тест-кейсів для перевірки форм. Під час власної реалізації розробником самостійно спроєктовано та написано класи:
    1. У `ScenarioEditing` та `SimulationViewModel.LoadScenario` реалізовано функціональний підхід із незмінними DTO (`ScenarioDefinition → ScenarioDefinition`): спочатку будується нова валідна топологія і лише після цього оновлюється стан симулятора, що унеможливлює часткове застосування некоректних правок.
    2. Розроблено клас `MapHitTester` для геометричного пошуку об'єктів під курсором (із пріоритетом вузлів над зонами та вибором найменшої вкладеної зони), а в `MapViewModel` додано механізм тимчасової фіксації масштабу (`BeginDrag`/`EndDrag`) та облік початкового зміщення курсора, щоб вузли не зміщувалися при виході за початкові межі сцени.
    3. У `SceneEditorViewModel` реалізовано захист від редагування під час активного відтворення безпосередньо в методі `Apply`, налаштовано безпечний парсинг числових полів через `InvariantCulture` із виведенням помилок валідації в UI без винятків та написано повний набір модульних тестів із 100% покриттям.
* **Запит 13 (Інтеграція файлового вводу/виводу в UI та каталог сценаріїв, Issue #26):** «Ізоляція файлових діалогів через інтерфейс, централізована обробка помилок читання/запису, генерація демонстраційних сценаріїв `scenarios/` та забезпечення 100% покриття тестами».
  * *Роль ШІ та доопрацювання:* ШІ згенерував конфігурації демонстраційних JSON-сценаріїв (`jammed-reroute.json`, `battery-depletion.json`, `network-partition.json`) з попереднім розрахунком очікуваних метрик, а також асистував у підборі негативних тест-кейсів для утримання 100% покриття коду (Line/Branch/Method). Розробником спроєктовано, інтегровано та верифіковано:
    1. Абстракцію `IFileDialogService` із реалізацією `AvaloniaFileDialogService` (виключеною з покриття) та тестовим дублером `StubFileDialogService`, що дозволило повністю протестувати сценарії вибору та скасування діалогів без запуску віконної підсистеми.
    2. Клас `FileOperationsViewModel` із єдиною точкою перехоплення очікуваних помилок диска та формату (`InvalidDataException`, `IOException`, `UnauthorizedAccessException`), яка гарантує збереження поточної сцени при відкритті пошкоджених файлів або звітів із порушеною контрольною сумою `.sha256`, а також блокує підміну сценарію під час активного прогону.
    3. Під час локальної перевірки усунено спробу виклику внутрішнього методу експортера з тестової збірки та виправлено розбіжність тексту помилки версії схеми у тестах імпорту; роботу діалогів і відображення резюме звітів перевірено вручну в UI.
